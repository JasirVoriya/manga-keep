技术架构

当前是单屏 Expo App，没有后端服务。远程公共数据来自静态托管， 用户收藏和本地目录留在设备本机。

UI 层

`LibraryScreen` 统一协调目录、记录、筛选、批量和弹窗；组件保持展示和输入职责。

数据层

`catalogRegistry` 拉远程 registry/manifest，`catalogStore` 合并本地、公共和内置目录。

持久化层

`collectionStorage` 保存收藏记录，`localCatalogStorage` 保存本地目录定义。

更新层

`versionCheck` 读取多源版本清单，比较版本并输出更新弹窗所需信息。

运行时数据流

启动后核心请求都是 best-effort，远程失败不阻塞本地收藏使用。

1启动 App

Expo 注册 `App`，渲染 `LibraryScreen`，界面先用内置默认目录兜底。

2加载本地状态

从 AsyncStorage 读取收藏记录和本地目录定义，只保留带目录 ID 的限定 key。

3拉公共目录

按 `catalogSources.priority` 请求 registry，失败后尝试下一源，并解析 manifest。

4合并目录

内置目录、远程目录、本地目录合并；同 ID 时本地目录优先级最高。

5检查更新

按 `updateManifestSources.priority` 请求 version.json，比较 `latestVersion` 和当前版本。

6用户操作

浏览、筛选、批量标记、编辑详情、导入导出都会回写本地 AsyncStorage。

下一步优先级

优先把“能分发、能更新、能远程加载封面”的闭环打通。

必须补

  • 配置真实公共目录源和真实 `version.json`。
  • 发布静态更新中心页面和 Android APK 下载入口。
  • 统一 App 名、包名、仓库名、图标和 JSON 标识。
  • 补同 ID 目录导入冲突确认 UI。

建议补

  • 真机验证远程封面后，移除包内封面依赖。
  • 接入系统文件导入导出和分享面板。
  • 增加范围批量操作，例如 `120-160`。
  • 增加目录管理页，支持编辑和删除本地目录。

以后再说

  • 账号与云同步。
  • App 内上传封面或公共目录。
  • 完整逐期编辑器。
  • 淘书辅助和订单管理。

架构风险

这些不是立刻阻塞，但继续扩展前最好心里有数。

远程源没有缓存

公共目录源失败时只能回退内置目录。后续可缓存上一次成功的 registry 和 manifest。

远程 JSON 没有签名

现在主要靠 schema 校验。后续可加 hash、签名或可信域名策略。

单屏职责变重

`LibraryScreen` 承担很多状态。功能增多后可拆 `useCatalogStore` 等 hooks。
